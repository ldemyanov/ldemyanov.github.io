# Сборка Astro и публикация в GitHub Pages

## Что делает локальная сборка

Команда **npm run build** запускает **astro build**, а затем **scripts/check-local-links.mjs**. Astro читает **astro.config.mjs**, синхронизирует Markdown-коллекции по схемам из **src/content.config.ts**, собирает CSS и клиентские скрипты через Vite и предварительно создаёт HTML для всех маршрутов. Страницы проектов и услуг получаются из Markdown-файлов и функций **getStaticPaths**. Интеграция **@astrojs/sitemap** добавляет sitemap; **src/pages/robots.txt.ts** создаёт robots.txt.

Результат — папка **dist/**. Astro копирует в неё файлы из **public/** по тем же URL, поэтому **public/images/...** превращается в **dist/images/...**. Скрипт проверяет локальные ссылки в готовых HTML, CSS, манифесте, sitemap и robots.txt; внешние адреса пропускает. Он учитывает завершающие слеши, параметры URL и закодированные имена файлов. При отсутствующем файле команда **npm run build** завершается с ошибкой. Повторить только проверку можно командой **npm run check:links**. Серверный процесс Astro после публикации не работает: GitHub Pages отдаёт готовые файлы.

Сайт использует корневой адрес **https://ldemyanov.github.io**. Он задан в **astro.config.mjs** и участвует в генерации canonical URL, Open Graph ссылок и sitemap. Для локальной альтернативной сборки адрес можно переопределить переменной **SITE_URL**. В конфигурации включены завершающие слеши и формат страниц в отдельных папках, например **dist/work/sbercraft/index.html**.

## Workflow репозитория

Файл [deploy.yml](../.github/workflows/deploy.yml) запускается при push в ветку **main** или вручную командой **Run workflow** в GitHub Actions.

1. **build** получает исходники через **actions/checkout@v4**.
2. **actions/setup-node@v4** устанавливает Node.js 22 и настраивает кэш npm.
3. **npm ci** устанавливает пакеты строго по **package-lock.json**.
4. **npm run build** создаёт **dist/** и проверяет ссылки. На этом шаге GitHub передаёт секрет **PUBLIC_WEB3FORMS_ACCESS_KEY** в окружение сборки. Ошибка проверки останавливает workflow до публикации.
5. **actions/configure-pages@v5** подготавливает Pages, затем **actions/upload-pages-artifact@v3** загружает **dist/**.
6. Задача **deploy** после успешной сборки публикует артефакт через **actions/deploy-pages@v4** в окружении **github-pages**.

Workflow получает только необходимые разрешения: чтение содержимого репозитория, запись в Pages и выпуск OIDC-токена для развёртывания. Параллельные запуски объединены в группу **github-pages**: новый запуск отменяет предыдущий незавершённый.

## Форма и секрет

В **Settings → Secrets and variables → Actions** должен быть секрет репозитория **PUBLIC_WEB3FORMS_ACCESS_KEY**. Его значение соответствует ключу Web3Forms из локального **.env**. Локальный файл **.env** не отправляется в GitHub.

**src/config/site.ts** читает переменную при сборке. Если она пуста, кнопка отправки формы остаётся отключённой; сама сборка при этом может завершиться успешно. Ключ с префиксом **PUBLIC_** встраивается в опубликованный HTML и доступен в браузере — это предусмотрено схемой Web3Forms. Личные пароли и серверные API-ключи так передавать нельзя.

Добавление или изменение секрета само по себе не запускает workflow. После этого в GitHub Actions нужно повторно запустить последнюю сборку (**Re-run all jobs**) либо запустить workflow вручную. Новый push в **main** также запускает сборку.

## Проверка публикации

После успешной задачи **deploy** откройте **https://ldemyanov.github.io/**. Проверьте главную, страницу проекта, изображения и форму контактов. Если изображения не открываются, сравните URL в коде с относительным путём файла после **public/**. Если форма отключена, проверьте имя секрета и запустите сборку заново. Ошибки синтаксиса Markdown frontmatter проявляются на этапе синхронизации коллекций.
